kii

kii gives a device access to Kii Cloud's REST API and Thing-IF:

  • authenticating the thing, by onboarding or logging in, and keeping its token valid through a session;
  • objects in buckets, with bodies of any size;
  • push messages over MQTT, from buckets, topics or straight to the thing;
  • Thing-IF states and firmware versions;
  • server code, and any other REST API call.

tio is built on kii and covers what most devices need: receiving commands and uploading states. Use kii directly for the rest.

kii does no networking of its own. It sends HTTP requests with khc, through socket callbacks the application supplies, and runs MQTT in a task the application creates.

  • Site: one of "JP", "US", "EU", "SG", "CN" and "CN3", or the host name of your application's site.
  • Buffer: required. Requests are built in it and responses read into it, so it must hold the largest of them: 4096 bytes are typically enough. Object bodies and Thing-IF states stream through callbacks instead, whatever their size. With a session, leave room after a request's body for the session to renew the token and send the request again; see Sessions.
  • JSON parser resource: tokens jkii parses responses with. 256 are enough for most responses. kii_set_cb_json_parser_resource() allocates exactly as many as each response needs instead.
  • Socket callbacks: see khc's socket callbacks. They are asked to connect to port 443, for TLS, or to port 80 when kii_enable_insecure_http() is set.

kii also uses the stream and response header buffers that khc does. Set them with kii_set_stream_buff() and kii_set_resp_header_buff(), or kii allocates them with malloc() for each request. Request headers are allocated with malloc() too, unless kii_set_cb_slist_resource() gives allocators of your own.

A kii_t makes one request at a time, and APIs block until the response has been read. Tasks making requests at the same time each need a kii_t of their own, with buffers of their own, attached to the same session.

Authenticate the thing

Most APIs are authorized with the thing's access token. Get one by:

  • Onboarding through Thing-IF, which registers the thing the first time and returns its ID and a token every time. Where MQTT is enabled, it also returns the MQTT endpoint the push task connects with.

    kii_code_t res = kii_ti_onboard(&kii, vendor_thing_id, password,
    "your-thing-type", "1.0.0", NULL, NULL);

The token is then kept in the kii_t, or in its session.

Sessions

Access tokens expire. A kii_session_t holds the thing's tokens for every kii_t acting as the thing, and renews the access token the way it was obtained:

  • From onboarding: by onboarding again through Thing-IF, when the server refuses the token. Onboarding issues no refresh token and no lifetime, and onboarding again leaves earlier tokens valid.
  • From a login or registration: with the refresh token, or by logging in again when there is none or the server refuses it. This happens shortly before the token expires, and whenever the server refuses it.

The server refuses a token with 403 and the errorCode WRONG_TOKEN. The refused request is then sent again with the new token, provided its body was built in the buffer set by kii_set_buff(), and the buffer has room after the body for the renewal: about 640 bytes, or 1150 to onboard again. Bodies streamed through callbacks, such as object bodies and Thing-IF states, can't be read again: the API reports the 403, the token already renewed, and calling it again uses the new token.

Attach the session to every kii_t acting as the thing before onboarding or logging in. The callbacks:

  • Lock: required. Keeps one task from renewing the token while another does, held for the length of the renewal request. It need not be recursive. On a platform where no other task using the session can run meanwhile, it can do nothing.
  • Monotonic clock: required. Milliseconds since any fixed origin, never going back, and not jumping when the wall clock is set. A 32-bit tick counter has to be extended to 64 bits. It is called only with the lock held.
  • Credentials: the vendor thing ID and password to onboard or log in again with. Without them, a token onboarding obtained is never renewed. The strings are not copied.
  • Author updated: called with the lock held whenever the tokens change. A refresh invalidates the tokens it replaces, so a device that keeps its tokens across a restart must save the author here before returning. It must not call kii APIs.

To restore a saved author, give it to the session with kii_session_set_author(). If onboarding obtained it, also call kii_session_set_renew_by_onboarding(), or the session renews it through Kii Cloud's token endpoint.

The tio README has lock and clock implementations for pthread.

Push

The push task keeps an MQTT connection to Kii Cloud's broker and hands every message it receives to a callback. The application creates the task, and supplies the MQTT socket callbacks and a buffer for messages:

kii_set_cb_mqtt_sock_connect(&kii, sock_cb_connect, &mqtt_sock_ctx);
kii_set_cb_mqtt_sock_send(&kii, sock_cb_send, &mqtt_sock_ctx);
kii_set_cb_mqtt_sock_recv(&kii, sock_cb_recv, &mqtt_sock_ctx);
kii_set_cb_mqtt_sock_recv_timed_out(&kii, sock_cb_recv_timed_out, &mqtt_sock_ctx);

  • MQTT sockets: blocking, with receive and send timeouts the same as those given to kii_set_mqtt_to_sock_recv() and kii_set_mqtt_to_sock_send(). When the receive timeout runs out, the recv callback returns KHC_SOCK_FAIL. The optional kii_set_cb_mqtt_sock_recv_timed_out() callback tells such a timeout from a lost connection, after which the task connects again.
  • Keep-alive: the second argument of kii_start_push_task(), in seconds. It must be longer than the socket timeouts; a few minutes is recommended. 0 turns it off, and a lost connection may then go unnoticed.
  • Task callbacks: creating the task and delaying it are required. kii_set_cb_task_continue() lets the application stop the task, and kii_set_cb_task_exit() is called as it exits, to free what it used. Both receive a kii_mqtt_task_info* saying what the task was doing and why it stopped. The tio README has implementations for pthread.

After onboarding, the task connects with the MQTT endpoint onboarding returned. Otherwise it installs push and gets an endpoint from Kii Cloud first. The task uses the kii_t it was started with until it exits: make requests from other tasks with another kii_t.

What reaches the thing:

  • Buckets and topics it subscribes to, with kii_subscribe_bucket() and kii_subscribe_topic(). kii_put_topic() creates a topic, and kii_delete_topic() deletes one.

  • Messages sent to a topic with kii_send_push_message(), and straight to a thing with kii_send_push_message_to_thing():

    topic.topic_name = "alerts";

Thing-IF

  • kii_ti_put_state() and kii_ti_patch_state() upload the thing's state, and kii_ti_put_bulk_states() and kii_ti_patch_bulk_states() several at once, read through a callback until it returns 0. tio_updater_t does this periodically.
  • kii_ti_put_firmware_version() and kii_ti_get_firmware_version() set and read the thing's firmware version.

Commands arrive as push messages. tio_handler_t parses them, runs their actions and sends the results back.

Other REST API calls

Any other call can be built with kii_api_call_*(). The path is the whole path, application ID included:

kii_api_call_start(&kii, "POST",
"/api/apps/your-app-id/buckets/readings/objects",
"application/json", KII_TRUE);
kii_api_call_append_body(&kii, "{\"temperature\":", 15);
kii_api_call_append_body(&kii, "21.5}", 5);
res = kii_api_call_run(&kii);
if (res == KII_ERR_OK) {
printf("status: %u\n", (unsigned)kii_get_resp_status(&kii));
}

KII_TRUE authorizes the call with the thing's token. Headers can be added with kii_api_call_append_header(). kii_api_call_run() returns KII_ERR_OK whatever the status, which kii_get_resp_status() gives. The response body is in the buffer, kii_get_resp_body_length() bytes long.

Results

APIs return KII_ERR_OK on success. KII_ERR_RESP_STATUS means the server answered with an error status, which kii_get_resp_status() gives, the response body being in the buffer. KII_ERR_SOCK_* come from the socket callbacks, and KII_ERR_TOO_LARGE_DATA from a request or response that doesn't fit in the buffer.

Building

kii is built as part of ebisu, as described in the top-level README. libkii includes khc and jkii.
