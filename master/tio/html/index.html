tio

With tio and Kii Interaction Framework, you can quickly implement IoT devices which supports following functionalities.

  • Read data from sensors and upload data to cloud periodically.
  • Receive remote control command from cloud and process it in your IoT device application.

tio consists of following modules.

  • tio_handler_t

Responsible for watching remote control command and propagate the command to IoT device application.

Once the module has been started, The loop inside the module keeps watching command arrival from the cloud.

  • tio_updater_t

Responsible for upload data read from sensors equipped to IoT devices.

Once the module has been started, The loop inside the module keeps asking for update by sensors periodically with the specified interval.

You can choose to run both tio_handler_t and tio_updater_t or either one.

Use tio_handler_t

Callback functions

Application developer needs to prepare following callback functions.

The system

tio_handler_t needs executing task asynchronously since it keeps waiting for commands sent to MQTT topic, and both it and tio_updater_t need to wait between attempts. The way of doing both varies in different environments, so the application gives tio an ebisu_system_t, from core.

It is a struct holding a pointer to a table of operations, which tio calls with the system itself as their first argument:

EBISU_TASK_ENTRY entry, void* entry_param);
void (*delay_ms)(ebisu_system_t* self, uint32_t msec);
uint64_t (*monotonic_ms)(ebisu_system_t* self);
} ebisu_system_ops_t;

  • task_create runs entry(entry_param) in a task of its own.
  • delay_ms waits. usleep(msec * 1000) would overflow above about 71 minutes, and return early on a signal.
  • monotonic_ms gives milliseconds since any fixed origin. It never goes back, and does not jump when the wall clock is set. A 32-bit tick counter has to be extended to 64 bits, or it wraps after about 49.7 days.

Typical implementation with pthread, as in platform's POSIX port, which an application on Linux or macOS can link as it is, with ebisu_posix_system(). A system with no state of its own can be one static object for everything:

static ebisu_task_code_t task_create(ebisu_system_t* self, const char* name,
EBISU_TASK_ENTRY entry, void* param)
{
pthread_t pthid;
if (pthread_create(&pthid, NULL, entry, param) != 0) {
return EBISU_TASKC_FAIL;
}
/* Nothing joins a task, so its thread has to go by itself when it ends. */
pthread_detach(pthid);
return EBISU_TASKC_OK;
}
static void delay_ms(ebisu_system_t* self, uint32_t msec)
{
struct timespec left;
left.tv_sec = msec / 1000;
left.tv_nsec = (long)(msec % 1000) * 1000000;
while (nanosleep(&left, &left) == -1 && errno == EINTR) {
}
}
static uint64_t monotonic_ms(ebisu_system_t* self)
{
struct timespec ts;
clock_gettime(CLOCK_MONOTONIC, &ts);
return (uint64_t)ts.tv_sec * 1000 + (uint64_t)ts.tv_nsec / 1000000;
}
static const ebisu_system_ops_t linux_system_ops = { task_create, delay_ms, monotonic_ms };
static ebisu_system_t system_ = { &linux_system_ops };
ebisu_system_t* linux_system(void)
{
return &system_;
}

Task continue callback

Task continue callback is used to determine whether to continue or exit task from the loop.

Task continue callback signature:

typedef bool (*KII_CB_TASK_CONTINUE)(void* task_info, void* userdata);
KII_CB_TASK_CONTINUE
bool(* KII_CB_TASK_CONTINUE)(void *task_info, void *userdata)

Implementation in example app:

bool _handler_continue(void* task_info, void* userdata) {
if (term_flag) {
return false;
} else {
return true;
}
}

term_flag is a variable determines whether to continue. Example app set it true when received SIGINT generated by Ctrl-C.

Note that we use atomic_bool type introduced in C11 since term_flag is referenced from signal handler, main thread and handler task thread (_handler_continue() is executed in handler task thread.)

Task exit callback

Task exit callback is called when task continue callback returns false or unrecoverable error occurs.

In this callback, you may need to free memories used for the handler task and other necessary steps when exiting task. The task has closed its MQTT connection by then, so don't close it here. The callback may call tio_handler_start() to start the task again.

Stop the task through the continue callback. A task ended any other way, such as by killing its thread, needs tio_handler_init() before starting again, as tio_handler_start() refuses while it counts as running. The same goes for tio_updater_t.

In the example app, we don't give allocated memory to tio_handler and pthread doesn't requires special treatment when exit loop, just set flag that indicate task has been exited safely.

void _handler_exit(void* task_info, void* userdata) {
printf("_handler_exit called\n");
handler_terminated = true;
}

handler_terminated is a variable indicates that resources allocated by handler is now all freed.

Details of memory management when exiting handler task, please refer to API reference of tio_handler_set_cb_task_exit().

We use atomic_bool here since the flag is referenced in main thread as well before exiting the process. (_handler_exit() is executed in handler task thread.)

You can see implementation with OpenSSL at platform's OpenSSL port, which an application on Linux or macOS can link as it is, as the linux-sample does.

The khc README has what these operations have to do that tio can't check for them, such as timeouts and SIGPIPE.

Note that, tio_handler uses MQTT(s) to receive remote control commands and uses HTTP(s) to send the result of command execution, so it takes two sockets: one for each. Both can have the same operations, but they must be different objects, as the two connections are open at the same time. Please also check Asynchronous task management section as well.

For both MQTT and HTTP, using them over secure connection is highly recommended. Our cloud supports non-secure connection for now. However, we may terminate supports of insecure connections in the future.

Notes about socket implementation used for MQTT.

Underlying socket implementation used for MQTT must be blocking mode, with a send timeout, and its recv timeout must be shared with tio_handler_t.

With a monotonic_ms in the system set by tio_handler_set_system(), tio_handler times the keep-alive by it, and sends PINGREQ early enough that a receive running into its timeout still ends within the keep-alive. Without one, it estimates the time since the last MQTT message it sent from the recv timeout and its own waits, which misses the time spent elsewhere, such as in the action callback.

MQTT keep alive interval must be larger than recv/ send timeout. Twice as large as recv/ send timeout works fine but recommend few minutes to avoid congestion.

tio_handler_set_mqtt_to_sock_recv(handler, 15);
tio_handler_set_keep_alive_interval(handler, 300);

When the recv timeout runs out with nothing received, the MQTT socket's recv should return EBISU_SOCK_FAIL. EBISU_SOCK_OK with 0 bytes means the broker closed the connection, and tio_handler connects again.

A lost connection makes recv return EBISU_SOCK_FAIL as well. To tell it from a timeout, give the socket the optional recv_timed_out operation: it returns true if the last receive timed out, and false if it failed otherwise, in which case tio_handler connects again. Without it, every EBISU_SOCK_FAIL while waiting for a command is taken for a timeout, and a lost connection is only noticed when a PINGREQ fails or goes unanswered; with a keep-alive interval of 0, never. See openssl_recv_timed_out() in platform's OpenSSL port.

userdata argument is a context object pointer given to tio_handler_start() method.

Alias, action name, action value and its type is defined by the feature called Trait.

Set-up tio_handler_t instance

Here's the set-up code extracted from example app. The full code can be checked handler_init() in example.c

tio_handler_init(handler);
tio_handler_set_app(handler, KII_APP_ID, KII_APP_HOST);
tio_handler_set_system(handler, ebisu_posix_system());
tio_handler_set_http_socket(handler, &http_ssl_ctx->base);
tio_handler_set_mqtt_socket(handler, &mqtt_ssl_ctx->base);
tio_handler_set_mqtt_to_sock_recv(handler, TO_RECV_SEC);
tio_handler_set_http_buff(handler, http_buffer, http_buffer_size);
tio_handler_set_mqtt_buff(handler, mqtt_buffer, mqtt_buffer_size);
tio_handler_set_keep_alive_interval(handler, HANDLER_KEEP_ALIVE_SEC);
tio_handler_set_cb_task_continue(handler, _handler_continue, NULL);
tio_handler_set_cb_task_exit(handler, _handler_exit, NULL);

Here's anatomy of set-up calls.

tio_handler_init call

This function must be called prior to any other functions of tio_handler_t.

tio_handler_set_app call

Set the Kii application information.

In the example, KII_APP_ID and KII_APP_HOST is defined as Macro. Those are used to identify work space in the cloud and the value is determined when you Kii Cloud App has been created. To create your Kii Cloud App, Sign-up to Developer console.

Set-up the system and sockets

tio_handler_set_system(handler, ebisu_posix_system());

Different socket objects, http_ssl_ctx and mqtt_ssl_ctx, are used since the connection and it's life-cycle is different between them. tio keeps a pointer to each object, so they have to outlive the handler's task. If your application allocates memory/ resources for them, application is responsible to free those memory/ resources.

tio_handler_set_http_socket(handler, &http_ssl_ctx->base);
tio_handler_set_mqtt_socket(handler, &mqtt_ssl_ctx->base);

Set-up buffers

tio_handler needs memory buffer to store HTTP/ MQTT payloads.

In this example, assigned 4KB for HTTP payloads and 2KB for MQTT payloads. This size may covers most use-cases. However, If you're remote command definition is more and larger, you may need to allocate larger size.

Note that buffer for HTTP and MQTT must be isolated. Passing overlapping memory causes undefined behavior.

tio_handler_set_http_buff(handler, http_buffer, http_buffer_size);
tio_handler_set_mqtt_buff(handler, mqtt_buffer, mqtt_buffer_size);

Set-up MQTT socket timeout.

tio_handler_t needs socket timeout in seconds to send MQTT PINGREQ periodically.

Note that application must implement socket timeout in the socket implementation. You can see example here

tio_handler_set_mqtt_to_sock_recv(handler, TO_RECV_SEC);

Set-up MQTT Keep Alive interval.

In the example, HANDLER_KEEP_ALIVE_SEC is defined as Macro and value is 300 (in seconds).

MQTT have mechanism called Keep Alive detecting stale connection between the MQTT broker.

tio_handler_t acts as MQTT clients and send PINGREQ to MQTT broker periodically with the specified interval. If PINGRESP from MQTT broker is not present, tio_handler_t would close the current connection and make fresh connection again.

If interval is set to 0, Keep Alive is turned off and no PINGREQ message is send to MQTT broker.

We highly recommend setting Keep Alive interval greater than 0 to detect disconnection. Recommended interval is few minutes since too small interval may cause network congestion and increases cloud cost.

MQTT keep alive interval must be larger than recv/ send timeout.

tio_handler_set_keep_alive_interval(handler, HANDLER_KEEP_ALIVE_SEC);

Set up a session

Access tokens expire. A kii_session_t holds the thing's token and, whenever the server refuses it, renews it the way it was obtained: by onboarding again through Thing-IF, with the thing's vendor thing ID and password. It then sends the refused request again. When the MQTT broker refuses the handler's credentials, the handler gets new ones the same way, as onboarding returns the MQTT endpoint along with the token. tio thus talks only to Thing-IF and the MQTT broker.

The tio_handler_t and the tio_updater_t of a device share one session, so that a token refused to either is renewed once, for both.

Here's the set-up code extracted from example.c.

kii_session_t session;
kii_session_init(&session);
kii_session_set_lock(&session, &session_lock.base);
kii_session_set_system(&session, ebisu_posix_system());
kii_session_set_cb_author_updated(&session, author_updated_callback, NULL);
if (tio_handler_set_session(&handler, &session) != TIO_ERR_OK ||
tio_updater_set_session(&updater, &session) != TIO_ERR_OK) {
printf("failed to set the session.\n");
exit(1);
}
// Used to onboard again when the server refuses the token, or the broker
// the MQTT credentials.
kii_session_set_password(&session, vendorThingID, password);

Set the session before onboarding, which then stores the token it obtains in the session. The samples onboard at each start. To use a token saved before a restart instead, give it to the session with kii_session_set_author(); the handler then gets its MQTT endpoint from Kii Cloud's API, as without onboarding, until the broker refuses the credentials.

Once the server refuses the password, the session doesn't try it again for 5 minutes, then twice as long after each further refusal, up to an hour: where the application limits login attempts, trying a wrong password whenever a token is refused would soon lock the thing out. Meanwhile requests refused for their token fail. Calling kii_session_set_password() again ends the wait.

Lock

Required. The handler's MQTT task and the updater's task both use the session, and the lock keeps one of them from renewing the token while the other does. It is held for the length of the renewal request. It need not be recursive. On a platform where the two tasks cannot run at the same time, its operations can do nothing.

An ebisu_lock_t is a pointer to its operations, embedded in the struct holding the mutex:

typedef struct {
ebisu_lock_t base;
pthread_mutex_t mutex;
} linux_lock_t;
static void lock(ebisu_lock_t* self)
{
pthread_mutex_lock(&EBISU_CONTAINER_OF(self, linux_lock_t, base)->mutex);
}
static void unlock(ebisu_lock_t* self)
{
pthread_mutex_unlock(&EBISU_CONTAINER_OF(self, linux_lock_t, base)->mutex);
}
static const ebisu_lock_ops_t linux_lock_ops = { lock, unlock };

platform's POSIX port has this one, ebisu_posix_lock_t, initialized with ebisu_posix_lock_init().

The system's monotonic clock

Required. The session times the expiry of tokens that have a lifetime, which those onboarding issues do not, with the monotonic_ms of the system set by kii_session_set_system(). It is called only with the session lock held, so it can count the wraps of a 32-bit tick counter without a lock of its own.

Author updated callback

Called whenever the session's token changes: after onboarding and after every renewal. A device that keeps its token across a restart saves the author here; onboarding again leaves earlier tokens valid, so one that onboards at each start, as the samples do, need not. It is called with the session lock held and must not call tio or kii APIs.

void author_updated_callback(const kii_author_t* author, void* userdata)
{
save_author(author);
}
kii_author_t

Keep the time

A device without a real-time clock needs the time to check the server's certificate in its socket callbacks. The handler and the updater give a ebisu_clock_t the time each response states, with tio_handler_set_clock() and tio_updater_set_clock(). They run in tasks of their own, so a clock they share needs a lock, set by ebisu_clock_set_lock(). That has to be a lock of its own, not the session's. The kii README describes the clock and how the socket callbacks use it.

Execute onboarding

For the first time, Step called onboarding is required. In this step, Identifier of IoT device (thing ID) is generated and stored in cloud.

After the step, thing ID and access token is returned to IoT device. By using thing ID and access token, cloud can identify the device when the remote command is sent to the device with the thing ID or sensor data sent from the device with the token.

This step can be skipped once thing ID and access token is stored by the IoT devices.

Alternatively, you can execute this step outside of the IoT Device and pass thing ID and access token to IoT devices. Typical example is using Mobile apps to execute the onboarding step and passing thing ID and access token to the devices via BLE, etc.

tio_code_t result = tio_handler_onboard(
&handler,
vendorThingID,
password,
thingType,
firmWareVersion,
layoutPosition,
properties);
tio_author_t author;
tio_handler_copy_author(&handler, &author);
/* thing ID and access token is stored in tio_author_t.
printf("thing ID: %s\n", author.author_id);
*/

Start module

Now, it's ready to start tio_handler_t module.

tio_handler_start(&handler, NULL, tio_action_handler, NULL);
  • author is taken from the session when one is set, and may be NULL. Without a session, pass the thing ID and access token obtained in the step of Onboarding, from tio_handler_copy_author().
  • tio_action_handler is the callback function pointer explained in Action callback
  • last argument is context object pointer can be referenced in action callback. Passing NULL since we don't use context object in this example.

This call results to execute asynchronous tasks created by Task callbacks. The name of the task initiated by this call is exported as macro KII_TASK_NAME_MQTT defined in kii.h.

Use tio_updater_t

Callback functions

The system, task callbacks, sockets

Similar to tio_handler_t.

tio_updater_t only uses HTTP(s) and does not use MQTT(s), so it takes one socket.

State read callbacks

tio_updater_t uploads the IoT device state such as sensor readings periodically with the specified interval.

When the specified interval elapsed, tio_updater_t execute callback function to read the latest state of the IoT device.

Application can implement the process reading values from sensors, etc.

Size callback.

Size callback is called to ask the size of new IoT device state. This callback is called before the read callback. If the returned size is 0, tio_updater_t skips updating device state.

With a session, it is called again when the server refused an upload for its token and the session renewed it: the upload is then made again, and the state read again from its beginning. The read callback must start over whenever this callback is called.

Signature of size callback:

typedef size_t (*TIO_CB_SIZE)(void* userdata);

userdata is context object pointer given to tio_updater_start() argument.

Read callback

Read callback is used to read actual IoT device state. Callback is repeatedly called until it returns 0.

typedef size_t (*TIO_CB_READ)(
char *buffer,
size_t size,
void *userdata);

  • size : Size of the buffer. Return how many bytes were written, which can be fewer than size, and 0 once the whole state has been read.
  • userdata : Context object pointer passed to tio_updater_start() function.

Expected format of the IoT device state is defined by Trait.

eg.)

{
"AirConditionerAlias" : {
"temperature" : 29,
"presetTemperature" : 20
}
}

  • temperature is number type property defined in the Trait.
  • presetTemperature is number type property defined in the Trait.

Execute onboarding

tio_updater_onboard() method is similar to tio_handler_onboard().

If you use both tio_handler_t and tio_updater_t for an IoT device, you just need to execute onboarding process from either one. No need to execute onboarding for both method since the thing ID bonding process just need to be executed once.

After the onboarding has been done, you can get tio_author_t instance from either tio_handler_t or tio_updater_t and pass it to tio_handler_start() or tio_updater_start() method. With a session shared by both, they take the author from it instead.

  • updater_file_ctx : Context object pointer referenced from both size callback/ read callback.

Asynchronous task management

tio execute multiple asynchronous tasks.

The name of tasks executed by tio_handler_t and tio_updater_t listed bellow.

Tasks executed by tio_handler_t.

  • KII_TASK_NAME_MQTT is a name of the task defined at kii.h and passed as argument when task_create of the system set by tio_handler_set_system() is called to create task/ thread.

    The task creation is requested once when the tio_handler_start() method is invoked.

    This task is responsible for connecting to MQTT with the endpoint onboarding returned, receiving messages from MQTT and propagating them to the app by the TIO_CB_ACTION callback, and sending MQTT PINGREQ periodically. If the handler was started without onboarding, or the broker refuses the credentials, it gets the MQTT endpoint through the REST API instead.

    This task calls the operations of the objects, and the callbacks, set by following APIs.

    • tio_handler_set_http_socket()
    • tio_handler_set_mqtt_socket() (Its recv_timed_out is optional. See Notes about socket implementation used for MQTT.)
    • tio_handler_set_system() (delay_ms)
    • tio_handler_start() (TIO_CB_ACTION callback)
    • tio_handler_set_cb_err() (Optional. In case set the error handler for debugging, etc.)
    • tio_handler_set_logger() (Optional. The logger the handler's requests, its MQTT task's events and the steps of a command that fail are logged to.)

    This task uses buffers set by following APIs.

    • tio_handler_set_http_buff()
    • tio_handler_set_mqtt_buff()

    Those two buffers must be separated and have no overlaps.

Tasks executed by tio_updater_t.

  • TIO_TASK_NAME_UPDATE_STATE is a name of the task declared in tio.h and passed as argument when task_create of the system set by tio_updater_set_system() is called to create task/ thread.

    The task creation is requested once when the tio_updater_start() method is invoked.

    This task is responsible for periodically updates the IoT device state with the specified interval.

    This task calls the operations of the objects, and the callbacks, set by following APIs.

    • tio_updater_set_socket()
    • tio_updater_set_system() (delay_ms)
    • tio_updater_start() (TIO_CB_SIZE, TIO_CB_READ callbacks.)
    • tio_updater_set_cb_error() (Optional. In case set the error handler for debugging, etc.)
    • tio_updater_set_logger() (Optional. The logger the updater's requests, and a state it couldn't upload, are logged to.)

    This task uses buffers set by following APIs.

    • tio_updater_set_buff()

Avoiding race condition

  • Above 2 tasks KII_TASK_NAME_MQTT and TIO_TASK_NAME_UPDATE_STATE would be executed in parallel. Therefore, if the callback implementation shares the resource that need exclusive access, you need to implement access control mechanism.
  • Both tasks call the callbacks of a session they share. Its lock guards the session itself.
  • You must prepare independent buffers which does not have overlaps.
