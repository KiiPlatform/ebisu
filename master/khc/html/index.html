khc

khc is a compact HTTP/1.1 client for resource-limited devices. kii and tio send their requests with it, so most applications use those and never call khc directly.

khc does no networking of its own: the application supplies socket callbacks, which also do TLS. Request and response bodies stream through callbacks and a buffer of fixed size, so neither has to fit in memory.

Supported features

  • Requests: any method, sent to the host's port 443, or 80 when khc_enable_insecure() is set. The request line carries the path, as in GET /path HTTP/1.1, followed by a HOST header and the application's headers. khc_enable_absolute_target() has it carry the whole URL instead, for a forward proxy that requests go through in plain HTTP.
  • Request bodies: sent with Transfer-Encoding: chunked, one chunk for each call to the read callback, until it returns 0, each chunk in one send with its size line and CRLF. With the length set by khc_set_req_body_length(), sent with Content-Length instead, as the read callback gives it. Without a read callback, the request is sent with Content-Length: 0. GET, HEAD and DELETE requests are sent without a body.
  • Responses: the status line and each header are passed to the header callback, and the body to the write callback. After an interim 1xx response, which goes through the header callback too, khc reads the final one.
    • A body sent with the chunked transfer coding is decoded, up to the end of the trailers; chunk extensions and trailers are ignored.
    • Any other body with a Content-Length ends there. Anything after either of these doesn't reach the write callback.
    • A body with neither is read until the server closes the connection, which it does after the body, as every request is sent with Connection: Close.
    • A response to HEAD, a 204 and a 304 end with their headers, whatever length they give.
  • Non-blocking sockets: a socket callback can return EBISU_SOCK_AGAIN, and khc calls it again with the same arguments: at once, or, with a system set by khc_set_system() that has a delay_ms, after KHC_AGAIN_WAIT_MS, 10 milliseconds unless defined otherwise.
  • A timeout for the whole request: khc_set_timeout_ms(), timed by the system's monotonic_ms, ends a request that goes on longer with KHC_ERR_TIMEOUT, however promptly each socket operation returns.
  • Cancellation: the callback set by khc_set_cb_continue() is asked between steps, and ends the request with KHC_ERR_CANCELLED when it returns false.

Limitations

  • One request per connection: no keep-alive and no pipelining. khc_perform() connects, sends the request, reads the response and closes the connection, blocking until it is done.
  • Nothing beyond HTTP framing: redirects are not followed, and 3xx responses reach the caller like any other. There's no support for compression or cookies, nor for proxies beyond khc_enable_absolute_target(). Authorization and content types are headers the application sets.
  • Transfer codings: a response whose last transfer coding is not chunked is refused with KHC_ERR_INVALID_RESPONSE, as is one with a malformed Content-Length, or with several that disagree. So is a chunked one with a Content-Length too, or from HTTP/1.0, which has no chunks, and one whose chunks' data isn't followed by a CRLF. Trailers are skipped, without being checked, and a connection closed among them still ends the response, the whole body having come.
  • Fixed-size request fields: a host longer than 127 bytes, a path longer than 255 and a method longer than 15 are refused with KHC_ERR_TOO_LARGE_DATA.
  • Long response headers: a header that doesn't fit in the response header buffer is skipped without reaching the header callback, which khc_get_resp_header_skipped() tells. If it is Content-Length or Transfer-Encoding, which khc needs, the request fails with KHC_ERR_TOO_LARGE_DATA.
  • Strict lines: the status line has to be HTTP/1.x, a space, three digits, and nothing more or a space and a reason phrase. Each header has to be a name of token characters, a colon right after it, and a value. A reason phrase or a value may hold spaces, tabs, visible ASCII and bytes from 0x80 up, and no other control character. A line that starts with a space or a tab, the obsolete line folding, isn't taken either. Anything else is refused with KHC_ERR_INVALID_RESPONSE: something else on the way, a proxy for instance, could read it another way than khc would.

Memory management

A khc instance holds its request line fields and state, and otherwise uses two buffers:

  • Stream buffer: holds each chunk of the request body and of the response body as it is read. Each part of the request body is sent in one send, over TLS at least one record, so a larger buffer means fewer records and fewer callbacks. 1024 bytes suit bodies of a few KB; for larger ones on a slow or metered link, 4096 or more. A chunk takes a few bytes of it for its size line and CRLF, so the read callback is offered that much less. Set it with khc_set_stream_buff(). Otherwise khc_perform() allocates 1024 bytes with malloc() and frees them before returning.
  • Response header buffer: holds one response header at a time, and must fit the status line, Content-Length and Transfer-Encoding. 256 bytes are enough. Set it with khc_set_resp_header_buff(). Otherwise khc_perform() allocates 256 bytes with malloc() and frees them before returning.

Request headers are a khc_slist, which belongs to the application and must stay valid until khc_perform() returns. khc_slist_append() allocates each node with malloc(), and khc_slist_free_all() frees the list. khc_slist_append_using_cb_alloc() and khc_slist_free_all_using_cb_free() take an allocator of your own instead, such as one handing out nodes from a static pool.

With both buffers set and the headers allocated by your own allocator, khc never calls malloc().

Making a request

The header and write callbacks are required. Each returns the number of bytes it handled; anything else aborts the request with KHC_ERR_HEADER_CALLBACK or KHC_ERR_WRITE_CALLBACK.

static size_t on_header(char* buffer, size_t size, void* userdata)
{
/* The status line first, then one header per call, without CRLF. */
printf("%.*s\n", (int)size, buffer);
return size;
}
static size_t on_write(char* buffer, size_t size, void* userdata)
{
/* Part of the body. Not null-terminated. */
fwrite(buffer, 1, size, stdout);
return size;
}

To send a body, use a method that has one and set a read callback. It is called until it returns 0:

typedef struct {
const char* data;
size_t length;
size_t sent;
} body_t;
static size_t on_read(char* buffer, size_t size, void* userdata)
{
body_t* body = (body_t*)userdata;
size_t remaining = body->length - body->sent;
size_t n = remaining < size ? remaining : size;
memcpy(buffer, body->data + body->sent, n);
body->sent += n;
return n;
}
body_t body = { json, strlen(json), 0 };
khc_set_method(&http, "POST");
khc_set_cb_read(&http, on_read, &body);
khc_set_cb_read
khc_code khc_set_cb_read(khc *khc, KHC_CB_READ cb, void *userdata)
Set read callback.

The callback may return less than size, but never more. When the body's length is known before it is sent, as here, khc_set_req_body_length() has it sent with a Content-Length rather than chunked, which some intermediaries handle poorly:

khc_set_req_body_length(&http, body.length);

The callback is then asked for no more than is left, and has to give all of it: returning 0 sooner is KHC_ERR_READ_CALLBACK.

To make another request with the same callbacks, call khc_reset_except_cb(), then set the request and the buffers again. To send the same request again, call khc_reset_except_request(), which keeps the buffers too. The read callback must then start the body over.

Socket callbacks

The socket is an ebisu_socket_t, declared in ebisu_socket.h, part of core: a pointer to a table of operations, which khc calls with the socket itself, self, as their first argument. An implementation embeds it in the struct holding the connection's state, and gets that back with EBISU_CONTAINER_OF(). khc keeps a pointer to the socket, so it has to outlive the requests. Each operation returns EBISU_SOCK_OK, EBISU_SOCK_FAIL, or EBISU_SOCK_AGAIN to be called again with the same arguments.

  • Connect (self, host, port): opens the connection, doing the TLS handshake unless the connection is insecure.
  • Send (self, buffer, length, out_sent_length): may send fewer bytes than asked, setting out_sent_length to how many it sent; khc sends the rest in later calls.
  • Recv (self, buffer, length_to_read, out_actual_length): sets out_actual_length to how many bytes it read. 0 means the server closed the connection.
  • Close (self): closes the connection. Once connected, it is called when the request ends, whether it succeeded or not. It is not called when connecting fails.

recv_timed_out, the fifth, is for kii's MQTT task, and khc doesn't call it, nor recv_wait, the seventh, optional too, with which the MQTT task waits for a packet a little at a time while it may have a message to publish. last_error, the sixth, optional too, says why the last operation that returned EBISU_SOCK_FAIL failed: a host that didn't resolve, an address that refused, TLS, a certificate refused, a timeout, a peer that closed, each with a detail such as errno or the certificate's verification result. khc asks it right after a failure, before closing, and khc_get_sock_error() gives the answer.

Implementations to start from:

  • platform's OpenSSL port: BSD sockets and OpenSSL, which applications can link as it is.
  • platform's Schannel port: Winsock and Schannel, which applications on Windows can link as it is.
  • esp32-sample: ESP-IDF's esp-tls, mbedTLS over lwIP.
  • freertos-sample: mbedTLS over FreeRTOS-Plus-TCP.

Writing callbacks

What khc leaves to the callbacks, which it can't check. linux-sample is the one to read for what socket callbacks have to do.

  • Timeouts: khc checks the request's timeout, if one is set, between socket operations, so a callback that blocks holds the request for as long as it blocks. Give sockets a send and a receive timeout. On Linux the send timeout bounds a blocking connect() too, but nothing in the system bounds looking up the host, which takes as long as the resolver does. platform's OpenSSL port bounds both, with its connect timeout.
  • A timeout is EBISU_SOCK_FAIL: khc calls a callback that returned EBISU_SOCK_AGAIN again, so returning it for a timeout has a server that stopped answering hold the request until the request's own timeout, if there is one, and for ever otherwise. EBISU_SOCK_AGAIN is for a non-blocking socket that isn't ready yet.
  • Cancelling from another task: the continue callback runs in the task performing the request, and reads what the other task sets, under a lock or as an atomic flag. It is asked at every step, so it has to be quick.
  • The end of the stream is EBISU_SOCK_OK with 0 bytes: that goes for a TLS connection the server closes without a close_notify too, which servers answering Connection: Close do. linux-sample shows how that looks to OpenSSL.
  • SIGPIPE: sending on a connection the peer has closed raises SIGPIPE, which ends the process. Ignore it, as linux-sample does in main(), or use MSG_NOSIGNAL or SO_NOSIGPIPE. A TLS library sends on its own too, as OpenSSL does when closing.
  • Close after a failure: the close callback is called on a connection that has failed as well, so it has to cope with one. OpenSSL's SSL_shutdown() must not be called after a fatal error, for one. What it returns doesn't change the request's result.
  • One request at a time: a khc isn't re-entrant. Each task making requests at the same time needs one of its own, with buffers and socket contexts of its own.
  • Callbacks running at once: those of different tasks do, so whatever they share needs locking. OpenSSL before 1.1.0 needs locking callbacks of its own, which linux-sample sets up.
  • Response size: khc passes the body to the write callback as it arrives, whatever its length. A callback that stores it has to set its own limit, by handling fewer bytes than given, which ends the request with KHC_ERR_WRITE_CALLBACK.

Results

khc_perform() returns KHC_ERR_OK once a response has been read, whatever its status: a 404 or a 500 is a response like any other, and khc_get_status_code() gives its status. Other results:

Result Cause
KHC_ERR_SOCK_CONNECT, KHC_ERR_SOCK_SEND, KHC_ERR_SOCK_RECV A socket callback returned EBISU_SOCK_FAIL, and khc_get_sock_error() says why, as the socket's last_error told it. KHC_ERR_SOCK_RECV also means the connection closed before the response ended, for which it says EBISU_SOCK_ERROR_CLOSED.
KHC_ERR_HEADER_CALLBACK The header callback handled fewer bytes than given.
KHC_ERR_WRITE_CALLBACK The write callback handled fewer bytes than given.
KHC_ERR_ALLOCATION A buffer khc allocates could not be allocated.
KHC_ERR_TOO_LARGE_DATA The status line, Content-Length or Transfer-Encoding doesn't fit in the response header buffer, or a chunk size line in the stream buffer, or the stream buffer has no room for a request chunk's data besides its size line and CRLF.
KHC_ERR_READ_CALLBACK The read callback returned more than it was asked for, or 0 before the length set by khc_set_req_body_length().
KHC_ERR_TIMEOUT The request went on longer than khc_set_timeout_ms() allows.
KHC_ERR_CANCELLED The continue callback returned false.
KHC_ERR_INVALID_RESPONSE The response isn't one khc can read: its status line isn't one, its Content-Length or Transfer-Encoding is malformed or unsupported, or a chunk size is malformed.
KHC_ERR_FAIL A socket, header or write callback isn't set, or a timeout is set without a system with a monotonic_ms, in which case nothing was sent.

Closing the socket comes last and doesn't change the result, as the server may already have acted on the request. khc_get_close_failed() says whether the close callback returned EBISU_SOCK_FAIL, or returned EBISU_SOCK_AGAIN once the request had timed out or been cancelled, when it is not called again.

khc_get_resp_date() gives the server's time from the response's Date header, as seconds since the epoch, for a device without a real-time clock. It takes the three forms RFC 9110 has recipients take, with UTC for GMT, and gives -1 for anything else, for several Dates that disagree, and for a date before the library's source, which no server running properly sends. The time is as trustworthy as the connection it came through, so verify the server's certificate in the socket callbacks.

Tracing

Configuring with -DKHC_TRACE=ON prints every request and response to stdout, headers and bodies included. That includes access tokens and passwords, so never enable it where its output is kept or shared.

Building

khc is built as part of ebisu, as described in the top-level README, as libebisu_khc, which links libebisu_core, and which libebisu_kii links.
