◆ KII_CB_AUTHOR_UPDATED

typedef void(* KII_CB_AUTHOR_UPDATED) (const kii_author_t *author, void *userdata)

Called when the tokens held by a session change.

Called after a login, onboarding or registration through any kii_t attached to the session, and after every renewal of the access token.

A refresh token can be used only once: renewing it invalidates the previous access token and refresh token. An author saved before the change can therefore no longer be renewed, so to restore the session after a restart the implementation must save the author before returning.

Called with the session lock held. The implementation must not call ebisu APIs.

Parameters
[in]authorThe author now held by the session.
[in]userdataContext object pointer passed to kii_session_set_cb_author_updated().

◆ KII_CB_SOCK_RECV_TIMED_OUT

typedef kii_bool_t(* KII_CB_SOCK_RECV_TIMED_OUT) (void *sock_ctx)

Callback tells whether the last receive on the MQTT socket timed out.

The recv callback set by kii_set_cb_mqtt_sock_recv() returns KHC_SOCK_FAIL both when its receive timeout runs out with nothing received, which is routine on an idle connection, and when the receive fails because the connection is lost. This callback tells the two apart. It is called right after such a KHC_SOCK_FAIL, before any other callback on the socket. See kii_set_cb_mqtt_sock_recv_timed_out().

Parameters
[in]sock_ctxContext object pointer given to kii_set_cb_mqtt_sock_recv_timed_out().
Returns
KII_TRUE if the receive failed because its timeout ran out, KII_FALSE if it failed for any other reason.

◆ kii_clock_t

typedef struct kii_clock_t kii_clock_t

The time of day, for a device without a real-time clock.

A TLS stack needs the time to check a certificate's validity period, and a device without a real-time clock has none until something tells it. Until then the clock has a floor, a time it is known not to be earlier than: when the library's source was built, or a time the application saved and set with kii_clock_set_floor(). Once a server states its time in a response to a kii_t the clock is set on with kii_set_clock(), or the application sets one with kii_clock_set_time(), the clock counts on from it with the monotonic clock.

So a check made before then has a lower bound of the time only: a certificate that expired before it is known to have expired, but one that is not valid until later cannot be told from one that is valid now. The same goes long after a time was given, 24 hours by default (kii_clock_set_exact_for()): a monotonic clock drifts, so what it counts is then a lower bound too. And if the monotonic clock goes back, the time given becomes the floor, until the next. A certificate refused as not valid yet while the clock had the time suggests the time fell behind: kii_clock_forget_time() makes it a lower bound until the next, so that the device connects again.

kii_clock_check_validity() applies that, for socket callbacks to use when checking the server's certificate, and kii_clock_get_time() gives the time and which of the two it is, for a TLS stack to check with itself.

Initialize with kii_clock_init(). The functions are safe to call from the socket callbacks, and from any task once kii_clock_set_cb_lock() has set a lock.

◆ kii_clock_forget_time()

void kii_clock_forget_time ( kii_clock_t *  clock)

Forget the time, keeping what was counted as the floor.

For the socket callbacks to call when their TLS stack refuses the server's certificate as not valid yet, while the clock had the time. On a device whose monotonic clock stops while it sleeps, the time falls behind, and a server that renewed its certificate meanwhile presents one that starts after it. Without a time of the server's, the clock could not catch up: the connection that would bring one is refused. Forgotten, the time becomes a lower bound, which kii_clock_check_validity() and the socket callbacks do not refuse a certificate for not having started by, so the next connection goes through, and its response gives the clock the time again.

What was counted on, less 1%, becomes the floor: the time is at least that, however the monotonic clock ran.

Parameters
[out]clockkii_clock_t instance.

Start MQTT task and watch message arrival. After succeeded, asynchronous task is started and cb_push is called when message is delivered to the thing. The task is created by the callback set by kii_set_cb_task_create(). If that callback is not set, or fails to create the task, no task is started and KII_ERR_CREATE_TASK is returned.

After kii_ti_onboard() returned an MQTT endpoint for the thing kii acts as, the task connects with that endpoint. Otherwise it installs push and fetches the endpoint first. If the broker refuses the credentials, it fetches new ones for the same installation; or, when kii's session renews its token by onboarding again, it onboards again for new ones, which renews the token too.

Parameters
[in,out]kiikii_t instance.
[in]keep_alive_interval_secMQTT Keep-Alive interval in seconds. MQTT keep alive interval in seconds. If 0, Keep Alive mechanism is disabled. Otherwise, pingReq is sent to MQTT broker periodically with the specified interval. Too short interval causes network congestion. We recommend to set this to few minutes. At most 65535, the largest MQTT can carry. It is taken as a uint32_t rather than a uint16_t so that a larger value is turned away here rather than cut down to its low 16 bits where the function is called.
[in]cb_pushCallback called when push message delivered.
[in]userdataContext object passed to cb_push.
Returns
kii_code_t. KII_ERR_FAIL if keep_alive_interval_sec is larger than 65535, and the task is not started.
