◆ KII_CB_AUTHOR_UPDATED

typedef void(* KII_CB_AUTHOR_UPDATED) (const kii_author_t *author, void *userdata)

Called when the tokens held by a session change.

Called after a login, onboarding or registration through any kii_t attached to the session, and after every renewal of the access token.

A refresh token can be used only once: renewing it invalidates the previous access token and refresh token. An author saved before the change can therefore no longer be renewed, so to restore the session after a restart the implementation must save the author before returning.

Called with the session lock held. The implementation must not call ebisu APIs.

Parameters
[in]authorThe author now held by the session.
[in]userdataContext object pointer passed to kii_session_set_cb_author_updated().

◆ KII_CB_MQTT_CREDENTIALS

typedef bool(* KII_CB_MQTT_CREDENTIALS) (kii_mqtt_endpoint_t *endpoint, void *userdata)

Asked for new credentials when the broker refuses those of a task started with kii_start_mqtt_task_with_endpoint().

Called in the task, after a CONNACK refusing them, with code 4 or 5. Write the new ones, or anything else of the endpoint that changes, into endpoint, each field terminated within its array, and return true to connect with them, after a wait as for any failed attempt. Return false to end the task with KII_MQTT_ERR_CREDENTIALS. It must not use the kii_t.

Parameters
[in,out]endpointWhat the task connected with, to be changed.
[in]userdataGiven to kii_set_cb_mqtt_credentials().
Returns
Whether to connect again with endpoint.

◆ KII_CB_MQTT_EVENT

typedef void(* KII_CB_MQTT_EVENT) (kii_mqtt_event_t event, uint32_t detail, void *userdata)

Told what happens in the MQTT task, for diagnostics.

Called in the task, as it happens, before what follows: the reconnection, the wait or the exit. It must return soon, and not use the kii_t. After KII_MQTT_EVENT_CONNECT_FAILED, _SEND_FAILED or _RECV_FAILED, the MQTT socket's last_error, asked from here, says why.

[in]detailMore of it, as the event says.

typedef struct kii_session_t kii_session_t

Tokens shared by the kii_t instances acting as the same thing.

Renews the access token when it is close to expiry or the server refuses it, the way it was obtained:

  • one onboarding obtained, by onboarding again through Thing-IF with the thing's credentials;
  • one a login or registration obtained, with the refresh token first, and by logging in with the thing's credentials when there is none or the server rejects it.

A request whose body was built in the buffer set by kii_set_buff() is then sent again; see kii_set_session().

◆ kii_set_mqtt_socket()

void kii_set_mqtt_socket ( kii_t * kii,
ebisu_socket_t * socket )

Set the socket the MQTT task connects to the broker on.

It must be blocking, with a send timeout, and with a receive timeout the same as given to kii_set_mqtt_to_sock_recv(): the task sends PINGREQ when the keep-alive interval requires between receives that time out.

Its recv returns EBISU_SOCK_FAIL when the receive timeout runs out with nothing received: the task takes EBISU_SOCK_OK with 0 bytes for the end of the stream, and connects again.

While the task waits for the next message, an EBISU_SOCK_FAIL from recv comes routinely from the timeout on an idle connection, and also from a lost connection. Only the socket can tell which, so the task asks its recv_timed_out. If that returns false, the task closes the socket and connects again. If it returns true, the task goes on waiting, and sends PINGREQ when the keep-alive interval requires. If the socket has no recv_timed_out, every such EBISU_SOCK_FAIL is taken for a timeout. A lost connection is then noticed only when a PINGREQ cannot be sent or goes unanswered, so with a keep-alive interval of 0 it is not noticed at all.

recv_timed_out is asked only in that wait. A receive that fails partway through a message, or while waiting for the broker to answer CONNECT or SUBSCRIBE, makes the task connect again whatever the cause.

[out]kiikii_t instance.
[in]socketThe socket. It has to outlive the task.

If you set the buffer by the method, it is used by every HTTP session initiated afterwards by methods such as kii_auth_thing(), kii_post_object(), etc., until the method is called again. Memory used by the buffer must therefore stay valid, and must not be used for anything else, as long as the kii_t instance is in use. To release it earlier, call the method with NULL first.

Set the system: tasks, delays and a monotonic clock.

The MQTT task is created with its task_create, and waits with its delay_ms. If it has a monotonic_ms, the task times the keep-alive by it. Otherwise it estimates the time by adding up its waits and receive timeouts, which misses the time spent elsewhere, such as in the push callback.

Start MQTT task and watch message arrival. After succeeded, asynchronous task is started and the callback set by kii_set_cb_mqtt_message() is called when message is delivered to the thing. The task is created by task_create of the system set by kii_set_system(). If there is none, or it fails to create the task, no task is started and KII_ERR_CREATE_TASK is returned.

After kii_ti_onboard() returned an MQTT endpoint for the thing kii acts as, the task connects with that endpoint. Otherwise it installs push and fetches the endpoint first. If the broker refuses the credentials, it fetches new ones for the same installation; or, when kii's session renews its token by onboarding again, it onboards again for new ones, which renews the token too.

At most 65535, the largest MQTT can carry. It is taken as a uint32_t rather than a uint16_t so that a larger value is turned away here rather than cut down to its low 16 bits where the function is called.
Returns
kii_code_t. KII_ERR_FAIL, with no task started, if keep_alive_interval_sec is larger than 65535, if the message callback, the system's delay_ms, a socket or an operation of one, or a buffer it needs is not set, or if the task of an earlier start is still running.
