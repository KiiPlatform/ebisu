kii

kii gives a device access to Kii Cloud's REST API and Thing-IF:

  • authenticating the thing, by onboarding or logging in, and keeping its token valid through a session;
  • objects in buckets, with bodies of any size;
  • push messages over MQTT, from buckets, topics or straight to the thing, and messages the thing publishes over MQTT;
  • Thing-IF states and firmware versions;
  • server code, and any other REST API call.

tio is built on kii and covers what most devices need: receiving commands and uploading states. Use kii directly for the rest.

kii does no networking of its own. It sends HTTP requests with khc, through socket callbacks the application supplies, and runs MQTT in a task the application creates.

  • Site: the host name of your application's site, as its settings give it: "api-jp.kii.com" for Kii Cloud's public site. A site of its own has a host of its own. "JP", which 1.x took for the public site, still works.

With a session, leave room after a request's body for the session to renew the token and send the request again; see Sessions.
  • Socket: an ebisu_socket_t, which kii keeps a pointer to; see khc's socket callbacks. They are asked to connect to port 443, for TLS, or to port 80 when kii_enable_insecure_http() is set.

kii also uses the stream and response header buffers that khc does. Set them with kii_set_stream_buff() and kii_set_resp_header_buff(), or kii allocates them with malloc() for each request. Request headers are allocated with malloc() too, unless kii_set_cb_slist_resource() gives allocators of your own.

A kii_t makes one request at a time, and APIs block until the response has been read. Tasks making requests at the same time each need a kii_t of their own, with buffers of their own, attached to the same session.

With a system set by kii_set_system(), the push task's, requests use it too. A socket that returns EBISU_SOCK_AGAIN is called again after its delay_ms of 10 milliseconds, rather than at once. With its monotonic_ms, kii_set_request_timeout() bounds each request as a whole, so that a server answering a byte at a time can't hold one for ever: past it, the request is KII_ERR_TIMEOUT.

Authenticate the thing

Most APIs are authorized with the thing's access token. Get one by:

  • Onboarding through Thing-IF, which registers the thing the first time and returns its ID and a token every time. Where MQTT is enabled, it also returns the MQTT endpoint the push task connects with.

Sessions

Access tokens expire. A kii_session_t holds the thing's tokens for every kii_t acting as the thing, and renews the access token the way it was obtained:

  • From onboarding: by onboarding again through Thing-IF, when the server refuses the token. Onboarding issues no refresh token and no lifetime, and onboarding again leaves earlier tokens valid.
  • From a login or registration: with the refresh token, or by logging in again when there is none or the server refuses it. This happens shortly before the token expires, and whenever the server refuses it.

The server refuses a token with 403 and the errorCode WRONG_TOKEN. The refused request is then sent again with the new token, provided its body was built in the buffer set by kii_set_buff(), and the buffer has room after the body for the renewal: about 640 bytes, or 1150 to onboard again. Bodies streamed through callbacks, such as object bodies and Thing-IF states, can't be read again: the API reports the 403, the token already renewed, and calling it again uses the new token.

kii_session_t session;
kii_session_init(&session);
kii_session_set_lock(&session, &session_lock.base);
kii_session_set_system(&session, &system);
kii_session_set_password(&session, vendor_thing_id, password);
kii_session_set_cb_author_updated(&session, author_updated_cb, NULL);
if (kii_set_session(&kii, &session) != KII_ERR_OK) {
/* No lock or clock set. */
}

Attach the session to every kii_t acting as the thing before onboarding or logging in. What it is given:

  • Lock: required, an ebisu_lock_t. Keeps one task from renewing the token while another does, held for the length of the renewal request. It need not be recursive. On a platform where no other task using the session can run meanwhile, its operations can do nothing.
  • System: required, for its monotonic clock: milliseconds since any fixed origin, never going back, and not jumping when the wall clock is set. A 32-bit tick counter has to be extended to 64 bits. It is called only with the lock held.
  • Credentials: the vendor thing ID and password to onboard or log in again with. Without them, a token onboarding obtained is never renewed. The strings are not copied. Once the server refuses them, they are not tried again for 5 minutes, then twice as long after each further refusal, up to an hour: where the application limits login attempts, trying a wrong password on every refused request would soon lock the thing out. Setting them again ends the wait.
  • Author updated: called with the lock held whenever the tokens change. A refresh invalidates the tokens it replaces, so a device that keeps its tokens across a restart must save the author here before returning. It must not call kii APIs.

To restore a saved author, give it to the session with kii_session_set_author(). If onboarding obtained it, also call kii_session_set_renew_mode() with KII_RENEW_BY_ONBOARDING, or the session renews it through Kii Cloud's token endpoint.

The tio README has lock and clock implementations for pthread.

Push

The push task keeps an MQTT connection to Kii Cloud's broker and hands every message it receives to a callback. The application creates the task, and supplies the MQTT socket and a buffer for messages:

char mqtt_buff[2048];
kii_set_mqtt_buff(&kii, mqtt_buff, sizeof(mqtt_buff));
kii_set_mqtt_socket(&kii, &mqtt_sock_ctx.base);
kii_set_mqtt_to_sock_recv(&kii, 15);
kii_set_system(&kii, &system);
kii_set_cb_task_continue(&kii, task_continue_cb, NULL);
kii_set_cb_task_exit(&kii, task_exit_cb, NULL);
kii_set_cb_mqtt_message(&kii, message_cb, NULL);
kii_code_t res = kii_start_push_task(&kii, 300);

  • Messages: kii_set_cb_mqtt_message() sets the callback the task gives each one to, which it needs. A kii_mqtt_message_t has the topic, terminated, and the payload, which isn't, both good until the callback returns; the QoS the message came at; whether the broker sent it as the topic's retained message, or again, for one the task may have had before; and its packet identifier at QoS 1.
  • MQTT sockets: blocking, with a send timeout, and a receive timeout the same as given to kii_set_mqtt_to_sock_recv(). When the receive timeout runs out, recv returns EBISU_SOCK_FAIL. The socket's optional recv_timed_out tells such a timeout from a lost connection, after which the task connects again.
  • Keep-alive: the second argument of kii_start_push_task(), in seconds. It must be longer than the socket timeouts; a few minutes is recommended. 0 turns it off, and a lost connection may then go unnoticed.
  • System: an ebisu_system_t, whose task_create creates the task and whose delay_ms it waits with. Both are required. kii_set_cb_task_continue() lets the application stop the task, and kii_set_cb_task_exit() is called as it exits, to free what it used. Both receive a kii_mqtt_task_info* saying what the task was doing and why it stopped. The tio README has implementations for pthread.
  • Events: optional, kii_set_cb_mqtt_event() sets a callback the task tells why it reconnects, waits or drops a message, as it happens: a request that failed, with its HTTP status, CONNACK's and SUBACK's codes, which send or receive failed, an unanswered PINGREQ, a message too large or malformed. Logging them is how to tell, in the field, a network that comes and goes from credentials the broker refuses.

After onboarding, the task connects with the MQTT endpoint onboarding returned. Otherwise it installs push and gets an endpoint from Kii Cloud first. A request that fails on the network, or with a 5xx or 429 response, is tried again, so a device can start the task before it has a network. Any other response ends the task, with the reason in kii_mqtt_task_info. The task uses the kii_t it was started with until it exits: make requests from other tasks with another kii_t.

The task speaks MQTT 3.1.1. kii_set_mqtt_version() sets MQTT 3.1 instead, for a broker with nothing later.

While it can't reach the cloud or the broker, the task waits longer between attempts: from about a second to at most five minutes, doubling each time, and for a share of that which depends on the thing, so that devices that lost their connection together don't all come back together. kii_set_mqtt_retry_wait_max() sets another longest wait. The wait goes back to the start once a connection is subscribed. The continue callback is still called every second, so the application can stop the task during a wait. A broker it can't reach after 8 attempts may have moved, so it then asks for the endpoint again.

The task subscribes at QoS 0 by default, so a message sent while it is reconnecting is lost. With kii_set_mqtt_qos(&kii, KII_MQTT_QOS_1), a message sent at QoS 1, such as a push message whose "mqtt" object has "qos": 1, is sent again until the task acknowledges it, once the message callback has returned: it can arrive twice. With kii_set_mqtt_clean_session(&kii, false) as well, the broker keeps the thing's session, and the QoS 1 messages sent while the task is away, reconnecting or stopped, until it connects again.

For a broker whose credentials the application has some other way, kii_start_mqtt_task_with_endpoint() starts the task with a kii_mqtt_endpoint_t of its own: the host, the port, the credentials, and the topic to subscribe to. The task neither installs push nor needs the HTTP socket or the buffer. kii_set_mqtt_client_id() sets a client identifier other than the topic, and when the broker refuses the credentials, the callback set by kii_set_cb_mqtt_credentials() gives new ones, or the task ends with KII_MQTT_ERR_CREDENTIALS. Brokers that hand out longer fields than kii_mqtt_endpoint_t holds can be given room by defining KII_USERNAME_MAX_SIZE, KII_PASSWORD_MAX_SIZE, KII_TOPIC_MAX_SIZE and KII_HOST_MAX_SIZE, alike for kii and everything using it. A session that renews by onboarding again then needs as much more room in the buffer, as onboarding's response carries the endpoint.

kii_set_mqtt_will() gives CONNECT a last will: a message the broker publishes if the connection is lost, rather than ended with the DISCONNECT the task sends when it stops, so that other clients can tell a device has gone. Whether it is published, and to whom, is the broker's.

Publish a message through the MQTT task, and wait until it is done.
  • When it is sent: the MQTT socket can't be used by two tasks at once, so the task sends the message between receives, once it is connected and subscribed. With a socket that has the optional recv_wait, as platform's ports do, the task waits for each packet KII_MQTT_RECV_WAIT_TURN_MS at a time, 100 milliseconds unless kii is built with it defined otherwise, and sends the message at the end of the turn. A shorter turn has it sent sooner, and wakes the task more often. Without recv_wait, a receive with nothing arriving lasts the timeout given to kii_set_mqtt_to_sock_recv(), so a shorter one has messages sent sooner. While the task reconnects, the message waits, up to the call's timeout.
  • One at a time: a call made while another's message isn't done waits for it, within its own timeout.
  • Twice, at QoS 1: a message whose PUBACK a lost connection took is sent again, with DUP, on the next connection, so the broker can get it twice.
  • Not from the task: a call from the task's callbacks would wait for the task, which waits for the callback, until the timeout runs out.

Whether the broker takes the message, and who receives it, is the broker's: one may acknowledge a message it drops. Publishing is the same with MQTT 3.1 and 3.1.1.

Writing task callbacks

What kii leaves to the system and the task callbacks, with platform's POSIX port to start from. The khc README has what socket callbacks have to do.

  • Creating the task: task_create returns EBISU_TASKC_OK only if it started. Nothing joins a task, so a thread has to be detached, or it stays behind when the task ends.
  • Delaying: delay_ms waits the whole time asked for, a signal or not. msec is a uint32_t, so usleep(msec * 1000) overflows above about 71 minutes.
  • Stopping the task: have the continue callback return false, or let an error end it. kii_start_push_task() refuses while the task is running, and a task ended any other way, such as by killing its thread, needs kii_init() before starting again.
  • The exit callback: the task has closed its connection by then, so only free what the application owns. It may start the task again.
  • The stack: tasks making requests need room for each request header line, and for a copy of khc, about 700 bytes on x86-64, when a session renews a token.

Thing-IF

  • kii_ti_put_state() and kii_ti_patch_state() upload the thing's state, and kii_ti_put_bulk_states() and kii_ti_patch_bulk_states() several at once, read through a callback until it returns 0. tio_updater_t does this periodically.
  • kii_ti_put_firmware_version() and kii_ti_get_firmware_version() set and read the thing's firmware version.

Commands arrive as push messages. tio_handler_t parses them, runs their actions and sends the results back.

Results

APIs return KII_ERR_OK on success. KII_ERR_RESP_STATUS means the server answered with an error status, which kii_get_resp_status() gives, the response body being in the buffer. KII_ERR_SOCK_* come from the socket callbacks, and kii_get_sock_error() says why, from the socket's last_error: a host that didn't resolve, a certificate refused, a timeout. KII_ERR_TOO_LARGE_DATA comes from a request or response that doesn't fit in the buffer. KII_ERR_TIMEOUT is a request that took longer than kii_set_request_timeout() allows.

kii_auth_thing(), kii_register_thing(), kii_ti_onboard(), kii_get_mqtt_endpoint() and a session's renewal send a password or a token, or receive tokens or MQTT credentials. After each, kii clears the buffers set by kii_set_buff() and kii_set_stream_buff() with ebisu_secure_zero(), so kii_get_resp_body_length() is 0 after one that succeeded. A response that refused the request holds no secret and says why, so it stays. kii clears its other copies as well: those on its stack, header lines as they are freed, and the MQTT buffer once CONNECT is sent. What it keeps to use, the kii_t's tokens and MQTT endpoint and a kii_session_t's, the application clears when done with them.

kii_get_resp_date() gives the server's time, from the Date header of the call's response, for a device without a real-time clock: khc's khc_get_resp_date(), which the khc README describes. It is as trustworthy as the connection it came through, so verify the server's certificate in the socket callbacks.

The time

A device without a real-time clock needs the time to check the validity period of the server's certificate in its socket callbacks. An ebisu_clock_t keeps it. Until a server states its time, it has a floor: a time it is known not to be earlier than. From the first response on, it has the time the response states, counted on with the monotonic clock.

ebisu_clock_t clock;
ebisu_clock_init(&clock, &system);
// Needed when kii_t of more than one task share the clock. Not the
// session's lock: the socket callbacks may use the clock while kii holds
// that one.
ebisu_clock_set_lock(&clock, &clock_lock.base);
// A time the device saved before, if any. Without one, the floor is
// shortly before the library's source was built.
ebisu_clock_set_floor(&clock, saved_time);
kii_set_clock(&kii, &clock);

The socket callbacks then check the server's certificate against it:

  • ebisu_clock_check_validity() checks a validity period. With the floor only, a certificate that ended before it has expired, but one that starts later cannot be told from one that is valid now, so only the end is checked. ebisu_time_from_civil() converts the dates a TLS stack gives.
  • ebisu_clock_get_time() gives the time, and whether it is the time or only the floor, for a TLS stack that checks validity itself: give it the time, and while it is only the floor, ignore a certificate not being valid yet.
  • ebisu_clock_forget_time(), when the server's certificate is refused as not valid yet while the clock had the time. That suggests the time fell behind, the monotonic clock having stopped while the device slept and the server having renewed its certificate meanwhile. Forgotten, the time becomes a lower bound, the next connection goes through, and its response gives the clock the time again. Without it, the connection that would bring the time is refused, again and again.

The chain and the host name are checked in full either way: the clock only decides the validity period.

The sockets of platform's OpenSSL and Schannel ports give their TLS stack the time, and those of the ESP32 and FreeRTOS samples check the validity periods themselves, mbedTLS not checking them: the ESP32 one after the handshake, the FreeRTOS one during it, in mbedTLS's verify callback.

A device that runs for a long time has the time again with every HTTP response. One that makes none for a while, only MQTT ones, has its time turn into a lower bound 24 hours after the last (ebisu_clock_set_exact_for() changes that), and a monotonic clock that goes back turns it into the floor: a monotonic clock drifts, and one cannot count on from a time when it goes back. A stale clock therefore never refuses a certificate as not yet valid, which could keep the device from connecting at all. The monotonic clock has to keep counting while the device sleeps, or the time falls behind while it still counts as exact. Saving the time now and then, and setting it with ebisu_clock_set_floor() after a restart, keeps the floor close to the time.
